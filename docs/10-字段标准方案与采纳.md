# 10 · 字段标准方案与采纳

> 文档状态：正式方案 v1.0（2026-09-03/04 grilling 定稿，2026-09-10 落档，2026-09-11 首版实现删除；决策见 [00 §7](00-术语表与总览.md) 第 50–62 条）
> 依赖：[00](00-术语表与总览.md)、[01](01-领域模型与协议.md)、[04](04-存储与同步规范.md)、[06](06-实施计划.md)、[09 §2](09-页面设计.md)
> 本册管「元字段 + 字段集」抽成独立标准之后，标准与 FlowCanvas 之间的关系：映射、采纳方式、全链路、差异与欠账。标准本身的规范在标准仓库的 `spec/`，本册不重复。

## 1. 定位与仓库

**是什么**：「元字段 + 字段集」的标准化解决方案 = 规范（fixtures 为权威）+ 单一官方 TS 实现 + 一致性用例。不是 FlowCanvas 的业务，不是自研产品，也不是开源库；FlowCanvas 是**第一个采纳者**，商品 SPU 属性是另一个对等的业务场景。流程编排、驱动、事件、快照都留在 FlowCanvas，不进标准。

**在哪**：暂无。首版实现（占位名 `field-standard`，包名 `@field-standard/*`）2026-09-04 完成、2026-09-11 拍板删除，待合适节点再实现（决策 61）；下面的目录结构保留作蓝图，首版原文在会话记录 `session_0181aZfiYPzeJbzThExZ36h7` 中。

```
spec/             README（规范条目）+ fixtures/（一规则一文件）+ schema/（zod 导出的 JSON Schema）
packages/core     canonical 模型、两张注册表（dataType 能力包 / 规则能力包）、合规门 checkMetaField、
                  组装 / 两层校验 / 筛选 / 影响分析、FieldSource 接入门面；无 DOM lib 编译，Node 可跑
packages/react    canonical → 渲染结构 RenderNode + useFieldForm（不含组件）
packages/antd     渲染器注册表 kind → 组件 + FieldForm
examples/commerce 采纳者示例：SPU 属性表接入（FieldSource）、注册 money 类型与 notIn 规则、换色块渲染器
```

三层分工（决策 58）：**core 出结构，react 推导渲染结构，antd 渲染**。渲染结构运行时算、不落数据；采纳者的每字段 UI 选择作为 react 层的输入。

## 2. canonical 与 01 的映射

01 定义的对象从此是 **FlowCanvas 的应用模型**；标准只认 canonical（决策 53）。两者的对应：

| 01（应用模型） | canonical（标准） | 说明 |
|---|---|---|
| `MetaField.metaFieldId` | `MetaField.id` | 命名差异，见 §5 |
| `fieldKey / name / helpText / dataType / defaultValue` | 同名 | 一致 |
| `numberConfig / enumOptions / itemType` | `params`（形状由该 dataType 的 `paramsSchema` 定） | 结构不同；单位组（01 §2.7 `grouped`）首版未实现，见 §5 |
| `FieldValidateRuleSet`（独立对象） | `MetaField.rules[]`（分区二） | 决策 44 判据保留，存储粒度交采纳者 |
| `FieldFilterConfig`（独立对象） | `MetaField.filter`（分区三） | 首版未做 `enabled` 与 `optionSource.kind = "field"`，见 §5 |
| `inputComponent`、`domain`、`createdAt / updatedAt` | **不进 canonical** | 留在应用模型；UI 提示由 react 层推导 |
| — | `ext`（平铺、透传、不解释） | 应用私货放这里；FlowCanvas 目前没有需要放的 |
| `NodeSchema.fieldBindings` | `FieldSet.bindings` | `defaultDriverBinding` 属流程层，不进标准 |
| `FieldBinding.metaFieldId / validations / runtimeComponent` | `fieldId / rules /（无）` | 其余属性同名同义；子组装规则一致 |
| dataType 11 种 | 核心集 9 种 | `multiline` 由 `describe` 降为 text、渲染提示走 react 层输入；`file` 缓入核心集，是采纳前置条件（决策 54，§3） |

**应用模型 `MetaFieldRecord`** = canonical 属性原样 + `projectId / domain / inputComponent / createdAt / updatedAt / referencedBy`（后者为服务端聚合的引用计数，列表「被引用」列用）。页面全程只碰应用模型；canonical 只在两个时刻产生：**要过门**（保存前校验）、**要被消费**（组装 / 校验 / 筛选 / 渲染 / 发布）。

## 3. FlowCanvas 的采纳方式

```ts
export const flowcanvasSource: FieldSource<MetaFieldRecord, Record<string, unknown>> = {
  // 剥掉 core 不读的属性；应用模型的 multiline 在进标准前降为 text（渲染提示不进 canonical，走下面的 overrides）
  describe: ({ projectId, domain, inputComponent, createdAt, updatedAt, referencedBy, dataType, ...rest }) => ({
    ...rest,
    dataType: dataType === "multiline" ? "text" : dataType,
  }),
  getValue: (values, key) => values[key],
  setValue: (values, key, v) => ({ ...values, [key]: v }),
};
const engine = createFieldEngine();
const fc = engine.adapt(flowcanvasSource);   // describeAll / toRecord / assign / validate / filter

// 渲染提示是 react 层的输入（决策 58）：multiline 与 inputComponent 从应用模型取，不进 canonical
const overrides = Object.fromEntries(records.map((r) => [
  r.fieldKey,
  { kind: r.inputComponent, props: { multiline: r.dataType === "multiline" } },
]));
```

- **`file` 字段是前置条件**：核心集暂无 `file`（决策 54），`describe` 遇到 `file` 没有类型可映射。因此 **FlowCanvas 整体切到标准引擎的前置条件是先定 `file` 的值形状并进核心集**——[01 §2](01-领域模型与协议.md) 自己也没定 file 的值形状（只说「移除 → null」、关系 `contains`），这是两边共同的欠账，定一次就够（[项目进度 §3](项目进度.md) 第 7 条）。在此之前**不做过渡方案**：不注册 file 扩展类型，也不让 file 字段绕过合规门。

- **抽屉保存**（09 §2.3）：`{ ...describe(current), ...form }` → `engine.checkMetaField` → issue 按 `path` 标到 `Form.Item`；改 `dataType` 时 `engine.dataTypeChangeImpact(old, newType, fieldSets)` 算出三处失效面（本字段 rules / filter、各字段集的绑定覆盖）→ 影响提示 → 确认后清理再保存。
- **规则二级页**（09 §2.6）：「添加规则」下拉 = `engine.rulesFor(record)`；「默认关系」= `engine.operatorsFor / defaultOperatorFor`；保存前 `checkMetaField({ ...describe(record), rules, filter })`。
- **`fieldKey` 唯一性**是唯一一条 core 管不了的规则（要看别的字段）：IndexedDB 阶段在 StorageAdapter 保存时校验，服务端阶段靠 `UNIQUE (project_id, field_key)`。
- **发布**（[03](03-发布与快照规范.md)）：固化 canonical 副本时剥掉 `filter` 分区——决策 47「筛选配置不进快照」原样成立。
- **服务端阶段**：core 零浏览器依赖，同一个包在 Node 里对 DTO 再过一次 `checkMetaField`，不信任客户端。

## 5. 再实现时的对齐清单（首版与 01 的差异）

首版实现（2026-09-04）与 01 的差异如下。2026-09-10 曾拍板「只改 docs、代码不动」登记为欠账；2026-09-11 实现删除后，本节转为**再实现时的对齐清单**，逐条过。

**命名差异**（标准 vs 01）：`id / metaFieldId`、`fieldId / metaFieldId`、`rules / validations`、`bindings / fieldBindings`、关系名 `ne / neq`、`isNotEmpty / notEmpty`、`startsWith`（标准多出、01 没有）。倾向：标准向 01 对齐，因为 01 是评审定稿，服务端把关系翻成 SQL 也按 01 的名字设计。

**首版未覆盖、01 已定的项**（再实现时须补）：

| 项 | 01 出处 | 首版现状 |
|---|---|---|
| 关系矩阵全集 | §6.1：`notContains / in / notIn`（text）、`notBetween`、`passed / notReached`（date）、`all / any / countAtLeast / lengthGte / lengthLte`（list）、object 子字段路径 | 只有子集 |
| datetime 边界语义 | §6.1.2：`after X` = ≥ 次日 00:00，`eq X` = 整天 | date 一致；datetime 按精确时刻比 |
| 数字单位组 | §2.7 `unit.kind = "grouped"` + 时间组换算 | 只有 `precision / unit: string` |
| 筛选配置 | §2.8 `enabled`（默认关）、`optionSource.kind = "field"`、`custom.options: string[]` | `filter.candidates: {value,label}[]`，无 `enabled`，无引用 enumOptions |
| `file` 类型 | §2 列为 11 种之一 | 值形状未定，缓入核心集（决策 54）；定稿后进核心集是 FlowCanvas 采纳的前置条件（§3） |
| 异步校验 | — | 规则 `check` 为同步；服务端唯一性等异步校验未进能力包 |

**待定**：再实现的时点、仓库与包的正式名字；FlowCanvas 接入改造（`packages/core/schema` 中字段部分改为依赖标准包、应用模型定义）随里程碑一做。
